# Case Study — Breaking the Circle Strategy

**渡劫 Ascension：让玩家从固定绕圈，转向观察、改线和资源取舍。** 阅读约 3–5 分钟。个人主导策划目标、范围与验收，Codex 辅助代码实现和验证；不是从零手写全部游戏。

## Context

我希望做一个可以实际试玩的策划作品，而不仅是一份机制清单。渡劫题材能把“观察危险、短时间生存、消耗有限资源”放进小型竞技场，不必先制作剧情、NPC 或开放世界。项目采用 Unity，复用 GameFactory Runtime；当前正式局为三分钟。

玩家的核心循环是：看地面预警，选择移动路线，决定是否消耗 Qi 使用 Dash 或 Shield，再寻找机会补给。

## Problem

早期持续沿圆周移动就能避开大部分雷击。攻击主要针对当前位置，玩家离开落点后便自然安全；单一行动能解决太多情境，Dash、Shield 和 Qi 容易成为可忽略功能。

问题不只是伤害低，而是玩家缺少改变行动的理由。如果只增加伤害或数量，可能让容错更低，却不一定让决策更丰富。

## Design Goal

希望“观察预警、改变路线、管理资源”在已测场景中优于固定绕圈或乱按技能，同时保留正常步行躲避的可能。技能应带来位置与承伤余量，不应成为每次危险都必须支付的通行费。

## Hypothesis

| 假设 | 预期改变的决策 |
| --- | --- |
| 在当前速度推算的未来落点预警，锁定后不再跟人 | 持续同向移动会进入危险；玩家可通过变向或 Dash 反制 |
| 用前方短墙和持续电场封路，而不是环形包围 | 玩家需要改线，后侧仍可能提供撤离空间 |
| 把部分 Qi 放在中央或当前路线之外 | 安全路线不再自动覆盖补给；取气要付出路线和时机成本 |

## Design Changes

1. 保留普通、连环和追踪雷，加入预测与封路的不同移动任务。根据阶段逐步增加组合压力，而非只有数量增长。
2. Dash 与 Shield 共用 Qi，分别解决位移和承伤。三功法通过费用、冷却、吸收量、持续时间与拾取收益形成取舍，未扩展为装备或技能树。
3. 普通补给在中央或偏离路线处选点，避开明显危险；风险掉落提供另一种恢复机会。后续随机背景雷不额外掉 Qi，避免新危险意外变成免费补给。
4. 对攻击数量、主要家族和安全空间作限制；有限方向采样检查普通步行出口。它只能筛掉部分不合理组合，不能保证所有未来随机状态绝对可解。
5. 后续 V1.1 收束正式局为 180 秒，保留 60 秒终劫，加入水区和移动雷球等路线压力。最新可读性调整删除常规雷击文字框，保留地面图形与关键 HUD，玩法数值没有随这次删除变化。

## Validation

必须分清三类证据：

- **Automated strategy：** 通过既有本地输入接口控制移动和技能，读取游戏状态，保存原生事件和输入。历史 T06 比较 A 观察但不用技能、B 固定绕圈、C 频繁 Dash、D 频繁 Shield、E 观察并组合技能/取气。脚本具有更完整的状态信息，不代表人类反应或阅读负担。
- **Developer playtest：** 我在实际 Play Mode 后提出预警、局长和文字遮挡反馈；这些是开发者体验观察，不能扩写成多人调研结论。
- **Human blind playtest：** 已建立[模板](BlindPlaytest.md)，尚未填入独立测试者结果，样本为 0。

Formal 与 Fast 使用同一机制，通过时长配置切换。Fast 用于更快覆盖阶段；正式局仍单独验证资源、流程和结算。高 HP 模型覆盖只验证规则，不作为正常生存证据。

原始记录：[固定绕圈](Evidence/v11-fast-circle-B-1790413010932707300-result.json)、[组合策略](Evidence/v11-fast-water-E-1790412850089174300-result.json)、[R1 正式局](Evidence/v11-r1-formal-E-1790517565184902500-result.json)。

**这不是玩家通关率，也不是严格单变量实验。** 输入与帧时序会改变后续布局，不能把两局差值都归因于某一机制。历史 T06 的精确观察策略也曾不用技能满血通关，因此结论是固定圈在已测情境中不再占优，而不是“所有无技能玩法必死”。这些历史结果不能冒充最新去文字版本的 Windows 验收；[当前验证归属](Playtest.md)单独列出。

## Reflection

自动策略能证明部分规则和流程工作，却不能证明好玩，也不能说明第一次玩的用户看懂了什么。只看最终 Qi 更容易误判经济，应同时看最低资源、技能失败、拾取路线和实际吸收，而不是把施放次数当作救命次数。

如果重做，我会更早安排独立玩家首次体验，再根据预警误读、死因解释和主动取气行为决定修改。也会让配置、Build、录像与测试版本一一对应，避免旧文档混入当前规格。

当前风雷是雷先结算、风后推动；它满足明确时序要求，但不应被夸成已经验证充分的空间协同。下一步优先验证现有组合与无文字预警，不继续堆新系统。

## AI-assisted Workflow

**Idea / Design Decision → Task Breakdown → Codex Implementation → Unity / Runtime Verification → Playtest Feedback → Iteration**

人的价值是定义问题、设计判断、控制范围、验收标准、解释反馈与决定下一轮。Codex 辅助 C#、Debug、自动测试、日志和文档；第三方 Runtime、模型、音效及 AI 生成背景分别保留[来源](../THIRD_PARTY_LICENSES.md)。本项目不宣称自研 Agent Framework、MCP Server、大模型或全自动游戏生成系统。
